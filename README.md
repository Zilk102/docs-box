# 📦 DocsBox

**Сверка условий договоров поставки — прямо в браузере.**
Сумма и срок по состоянию на дату проверки, с цитатой и переходом к абзацу исходного документа.
Приложение **ничего не хранит**: команда работает с одним файлом базы на своём сервере.

## Что делает

| | |
|---|---|
| 📄 **Загрузка TXT** | Договоры, допсоглашения, письма — перетащите файлы или выберите на диске (UTF-8 и Windows-1251). |
| 🧮 **Таблица по договорам** | Номер, поставщик, сумма, срок поставки на дату проверки, неустойка. |
| ⚖️ **Учёт статуса документов** | Условия меняет только **подписанное обеими сторонами** допсоглашение, **вступившее в силу** к дате проверки. Письма, проекты и «будущие» допсоглашения показываются отдельно как *«не согласовано / вступит позже»*. |
| 🔎 **Проверяемость** | У каждого значения — имя файла, **точная цитата** и кнопка перехода к абзацу (подсветка в просмотре документа). |
| 🚫 **Никаких догадок** | Нет значения — «нет данных». Аванс и внутренний лимит бюджета не принимаются за стоимость (и показываются как «не принято» с причиной). Спорное — «нужна проверка». |
| ❓ **Вопросы** | «Значение поля по договору» и «поставка раньше даты + есть ли несогласованные изменения срока». |
| 👥 **Общая база** | Несколько специалистов работают с одним файлом на сервере одновременно, изменения подтягиваются каждые 5 секунд. |

## Быстрый старт

**Онлайн:** откройте [демо](https://zilk102.github.io/docs-box/#demo) — демо-набор загрузится сам.

**Локально** (нужен Node 18+, зависимостей нет):

```bash
git clone https://github.com/Zilk102/docs-box.git
cd docs-box
npm start            # http://localhost:8080  (любой статический сервер подойдёт)
```

Тесты: `npm test` (42 теста: разбор, сверка, слияние базы, реальный HTTP-сервер и параллельные писатели).

### Пример сценария
1. Откройте страницу → **«Загрузить демо-набор»** (или перетащите файлы из [`examples/documents`](examples/documents)).
2. Дата проверки — `10.03.2026`. По STN-101 действует срок **30.04.2026** (изменён ДС №1; проект ДС №2 не учтён), по STN-102 сумма **840 000 ₽** (не аванс 252 000), по STN-103 сумма — **нет данных** (лимит 600 000 ₽ не принят).
3. Нажмите на любую «плашку» с именем файла — справа откроется документ с подсвеченной цитатой.

## Как работает общая база

Страница **не содержит бэкенда и не пишет в localStorage/cookies/IndexedDB**. «База» — один JSON-файл с исходными текстами документов (значения всегда пересчитываются из текстов, поэтому не могут «протухнуть»). Три способа работать с ней:

| Способ | Для чего | Как |
|---|---|---|
| **Сервер по URL** | Команда на разных компьютерах | Укажите адрес `https://…/db.json` (и, если нужно, `Authorization`). Страница делает `GET`/`PUT` с `ETag`/`If-Match`. Ссылка вида `…/#db=<url>` подключает коллегу в один клик. |
| **Файл на диске / сетевая папка** | Общий диск, OneDrive, Яндекс Диск | Chrome/Edge: «Открыть файл базы» (File System Access API). |
| **Только импорт/экспорт** | Разовая работа, офлайн | «Импорт базы» / «Экспорт базы» (JSON). Импорт — *слияние*, а не замена. |

**Одновременная работа.** База — набор записей с метками времени. Слияние — объединение по `id` (хэш имени и текста), побеждает более свежая запись, удаление — «надгробие». Запись условная (`If-Match`): если файл кто-то успел изменить, клиент перечитывает его, **сливает и повторяет** — чужие загрузки не теряются. Слияние коммутативно и идемпотентно (проверено тестами), а каждый клиент хранит свою копию в памяти и дописывает недостающее, поэтому даже сервер без `ETag` не приведёт к потере данных. Загрузка файла с тем же именем и другим текстом = новая версия, старая заменяется.

### Сервер для общей базы

Нужен любой HTTP-сервер, который отдаёт и принимает один файл и разрешает CORS для адреса вашего Pages: `GET`, `PUT`, заголовки `ETag`, `If-Match`, `If-None-Match`, `Authorization`. Подходят WebDAV (Nextcloud, nginx `dav`), S3-совместимые хранилища и референсный сервер из этого репозитория (без зависимостей):

```bash
TOKEN=мой-секрет ALLOW_ORIGIN=https://zilk102.github.io DB_FILE=./data/db.json node server/server.mjs
# → http://localhost:8787/   в приложении: адрес http://localhost:8787/db.json, Authorization: Bearer мой-секрет
```

Если страница открыта по HTTPS (GitHub Pages), сервер тоже должен быть на HTTPS (исключение — `localhost`). Токен хранится только в памяти вкладки и не попадает в ссылку.

## Как устроено извлечение

Без LLM и без сети — **правила + реестр полей** ([`src/core/fields.js`](src/core/fields.js)). Документ делится на абзацы и предложения (с точными смещениями), каждое предложение проверяется правилами поля; результат — значение + цитата. Новое условие (например, пени) добавляется описанием одного поля. Подробности и границы — ниже в записке.

```
TXT ──► parse.js ──► кандидаты значений + статус/даты/стороны ──► resolve.js ──► таблица, вопросы
         ▲ fields.js (правила полей)          (учёт подписания и вступления в силу на дату проверки)
         └─ db.js ◄──► sync/ (HTTP ETag · файл · импорт/экспорт) ◄──► общий файл базы
```

## Известные ограничения
- Только TXT; OCR, PDF/DOCX не поддерживаются. Только рубли.
- Формат «договор + допсоглашение, пункты изложены целиком» (как в примерах). Нетиповые формулировки → «нужна проверка» или «нет данных», а не догадка.
- Суммы из приложений/спецификаций не читаются, пока приложение не загружено как TXT.
- Файловое хранилище: окно гонки между проверкой и записью — миллисекунды; конфликт лечится слиянием при следующей синхронизации.
- Опрос раз в 5 с, без push-уведомлений. Права доступа — на стороне сервера (токен), внутри базы ролей нет.

## Записка Product Owner

**Для кого.** Специалист по закупкам, который сверяет условия поставки и не хочет перечитывать пачку документов. Главное для него — не «ответ», а *ответ, который можно проверить за 10 секунд*.

**Пять вопросов клиенту перед развитием**
1. Какие форматы реально приходят (PDF-сканы, DOCX, 1С-выгрузки)? Это определяет, нужен ли OCR.
2. Где «источник правды» о подписанных документах (СЭД, 1С, почта) и есть ли статус подписи в метаданных, а не в тексте?
3. Какие ещё условия нужны в таблице (НДС, этапы поставки, валюта, гарантия, штрафы) и в каком порядке важности?
4. Какая цена ошибки: что хуже — пропущенное изменение или лишний «нужна проверка»?
5. Требования к данным: можно ли держать тексты договоров на внешнем сервере, кто и что вправе видеть?

**Допущения.** Дата проверки задаётся пользователем и общая для базы; допсоглашение вступает в силу в указанную дату (без даты — «нужна проверка»); имена файлов и дата загрузки приоритет не определяют; при двух допсоглашениях с разными датами побеждает более поздняя дата вступления; договоры одного формата с учебными.

**Две метрики**
- *Доля значений, принятых без правки* (точность извлечения по размеченной выборке) и отдельно *доля ложных «уверенных» значений* (должна стремиться к 0 — это основной риск).
- *Время «от загрузки до проверенного значения»* (клик по цитате вместо перечитывания) и доля договоров, закрытых без ручного чтения.

**Ключевые технические решения и компромиссы**
1. **Правила вместо LLM.** Детерминированно, бесплатно, работает офлайн и объясняется цитатой; цена — хрупкость к нетиповым формулировкам (смягчено «нужна проверка» вместо догадки). LLM имеет смысл как второй проход для спорных случаев.
2. **Статический клиент + общий файл вместо бэкенда.** Нет сервера для поддержки и нет хранения данных в приложении; цена — права доступа и аудит делегированы серверу файла, масштаб ограничен размером одного JSON.
3. **База хранит исходные тексты, не результаты; слияние по записям.** Результат всегда соответствует тексту и правилам; параллельная работа без блокировок; цена — пересчёт на клиенте при каждой загрузке.

**100 000 документов и права доступа.** Один JSON не масштабируется: нужны серверная БД и индекс (полнотекстовый + структурированные поля), извлечение при загрузке и кэш результатов, постраничная выдача, версии документов и аудит. Права — на уровне организаций/договоров (RBAC/ABAC), шифрование, SSO; клиент остаётся тонким. Ядро разбора (`src/core`) переносится на сервер без изменений.

**Три следующих улучшения (по приоритету)**
1. Поддержка PDF/DOCX и OCR + разметка эталонной выборки для измерения метрик.
2. Приложения/спецификации и этапы поставки (несколько сроков и сумм на договор), валюта и НДС.
3. LLM-второй проход для «нужна проверка» с обязательной цитатой и верификацией (цитата должна дословно найтись в тексте) + уведомления/комментарии в общей базе.

## Структура репозитория

```
index.html            страница (GitHub Pages отдаёт корень)
src/core/             разбор, правила полей, сверка, вопросы, формат и слияние базы (без DOM)
src/sync/             синхронизация: HTTP (ETag), файл на диске, цикл read-merge-write
src/ui/               интерфейс (без сборки, без зависимостей)
server/server.mjs     референсный сервер общей базы
examples/             учебные документы и demo-db.json
tests/                node:test, 42 теста
```
